# 开源规范与发布清单

## 发布前必须具备

- `LICENSE`：由维护者选择许可证后加入。尚未选定前，不应声称项目已经以某种许可证开源。
- `CONTRIBUTING.md`：开发环境、分支/提交要求、测试要求、提交 issue 和 pull request 的方式。
- `CODE_OF_CONDUCT.md`：协作行为准则。
- `SECURITY.md`：私密漏洞的报告渠道；禁止在公开 issue 中提交账号、Cookie、Token、签名 URL 或教材文件。
- `CHANGELOG.md`：记录面向用户的版本变化。
- GitHub Issue 与 Pull Request 模板：缺陷复现、功能建议、隐私/安全检查项。

## 仓库卫生

- `.gitignore` 必须排除 `.electron-data`、下载目录、`.part`、浏览器 profile、日志、截图中的个人信息、授权信息和本地数据库。
- 提交前检查 Git 历史与发布产物，确认不含真实 PDF、Cookie、Token、授权头、签名下载地址、账号信息或完整网络报文。
- 示例数据使用脱敏/虚构数据；问题复现材料只提供最小必要字段。
- 依赖锁文件应提交；依赖升级、Electron 升级和安全更新应有可复现测试。

## 安全与隐私基线

- 保持 Electron `contextIsolation`，关闭 renderer 的 Node.js 集成，preload 仅暴露必要 IPC。
- IPC 对输入做校验，错误信息去除敏感 URL、请求头、Cookie 和会话内容。
- 会话数据只存本机；正式发布版使用操作系统提供的受保护存储，不写明文 Token 文件。
- 不收集遥测数据；若未来添加诊断或崩溃报告，必须默认关闭、明确告知且脱敏。

## 版本与发布

- 遵循语义化版本：破坏性行为变化升主版本，兼容功能升次版本，修复升补丁版本。
- 每次发布至少执行类型检查、构建和关键下载流程验证；发布说明写清新增、修复、已知限制和迁移影响。
- Windows 安装包或便携包必须不携带开发期 session、用户资料、下载任务或缓存目录。
- 代码签名、自动更新和可复现构建是正式公开发布前的目标，不应以未签名测试包替代安全承诺。

## 贡献边界

- 欢迎 UI、可访问性、测试、文档、目录解析健壮性和本地任务管理贡献。
- 不接受绕过平台登录、访问控制或资源权限的实现。
- 不接受把用户凭据、下载资源或可复用授权链接提交到仓库的贡献。
- 平台适配器变化需要同时审查隐私影响、错误处理和用户可见状态。
